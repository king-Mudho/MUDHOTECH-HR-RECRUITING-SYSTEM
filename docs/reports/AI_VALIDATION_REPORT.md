P10-T03, 2026-11-17. Engine **`0.3.1`** (was 0.3.0), matching thresholds **`2026.11.2`** (was
`2026.11.1`) — both calibrated in this task. Synthetic data only: the labelled corpus in `backend/fixtures/synthetic_cvs`

## 3. Calibration

### 3.1 Listed-only skills (EC-DOC-24)

A skill that appears only in the CV's skills list scored **50** ("partial"); used in a role or
project 100; mentioned in the profile 75; inferred from a related skill up to 75. Two problems
showed up in the pilot benchmark (D-008):

1. **Inversion.** An *inferred* match (75) out-scored an *explicit* listed one (50): a CV listing
   "Python" scored lower than one that only mentioned Django.
2. **Skills-heavy rubrics bury qualified people.** HR vacancies often make most essentials skills
   (the demo Software Developer vacancy: Python, SQL, Git essential). With 50 per listed skill the
   total stays below the 70 threshold even when every essential is present, and the candidate
   lands in *lower match*.

The calibration sweep (`calibrate.py`) evaluates every readable CV against the corpus rubric and a
skills-heavy *vacancy* rubric (role skills essential, one "demonstrable related work" criterion,
two preferred extras CVs rarely evidence). Scores must stay on the rubric bands (0/25/50/75/100),
so the candidates were 50 and 75:

| Listed-only score | Corpus recall | Corpus recommended | Vacancy recall | Vacancy recommended | Not-suitable recommended |
|---|---|---|---|---|---|
| 50 (2026.11.1) | 100 % | 61 % | **73 %** (12 suitable in lower match) | 34 % | 0 |
| **75 (2026.11.2)** | 100 % | 61 % | **100 %** | 61 % | **0** |

**Decision:** `skill_listed_only = 75`, config version `2026.11.2`. A listed skill is still below one
used in a role (100), never above an explicit statement, and the explanation now says plainly
"*X is listed among the skills … use in a role or project was not found*" (kind *partial*), so a
reviewer never reads a listed skill as demonstrated. Existing evaluations keep `2026.11.1`; HR
re-evaluates by starting a screening run (new versions, never overwritten).

### 3.2 Semantic thresholds

Local model `sentence-transformers/all-MiniLM-L6-v2` (CPU), full sweep in
`docs/reports/calibration_2026-11-17.md`.

**Evaluation (criterion ↔ CV skill, `semantic_skill_threshold`).** Swept 0.70–0.86 with both
listed-only scores: bands did not change at any value, because semantic matching is consulted only
when no exact, alias or taxonomy-relation match exists, and those cover the corpus rubrics.
**Kept at 0.78**; semantic matches remain *inferred* and capped at 50.

**Extraction (CV phrase ↔ taxonomy skill, `DEFAULT_THRESHOLD`).**

| Threshold | Skill precision | Skill recall | Equivalent-wording recall |
|---|---|---|---|
| off | 0.996 | 0.998 | 0.738 |
| 0.60 | 0.996 | 0.998 | 0.786 |
| **0.65** | 0.996 | 0.998 | **0.762** |
| 0.70 | 0.996 | 0.998 | 0.738 |
| 0.75 (previous) | 0.996 | 0.998 | 0.738 |
| 0.80 | 0.996 | 0.998 | 0.738 |

At 0.75 semantic matching added nothing. **Decision: 0.65**, engine version **0.3.1** (extraction
output changes, so runs are re-versioned). 0.60 found more, but only 9 CVs test equivalent wording
and precision is measured on skills-list sections only, so one step of margin is kept; revisit with
real data. Equivalent wording remains the weakest extraction metric (0.76) — HR-listed equivalents
on criteria (§3.3) are the reliable mechanism.

### 3.3 Rubric equivalents

"REST API design" did not match "REST APIs" in a CV: criteria match taxonomy skills and the
equivalents HR lists, by design (no fuzzy guessing on essentials). The demo vacancy now lists
equivalents for its preferred criteria (REST, frontend, cloud); the recruiter guide tells HR to add
the wordings they accept.

## 4. Missed-qualified analysis

| Case | Before (2026.11.1) | After (2026.11.2) | Cause |
|---|---|---|---|
| Corpus rubric, suitable → lower match | 0 / 44 | 0 / 44 | — |
| Vacancy rubric, suitable → lower match | **12 / 44** | 0 / 44 | listed-only skills at 50 kept totals < 70 (§3.1) |
| Pilot (demo vacancy, 100 applications, full Django pipeline) suitable developers → lower match | 4 / 7 (2 recommended) | **0 / 7** (6 recommended, 1 review needed) | §3.1 + equivalents (§3.3) + semantic model on |

Suitable candidates routed to *review needed* rather than *recommended* (17/44 on both rubrics) are
not misses — a person still reviews them first — but they are where reviewer time goes. Their band
reasons: low coverage 10, low confidence 6–14, prompt-injection flag 4 (deliberate test CVs),
unsupported language 2, unknown essentials 3.

## 5. Failure taxonomy (band reasons, corpus rubric, 135 readable CVs)

| Reason | Suitable | Possibly suitable | Not suitable | What it means |
|---|---|---|---|---|
| Essentials unknown | 3 | 32 | 44 | an essential has no evidence — unknown, never a fail (principle 3) |
| Low coverage | 10 | 12 | 21 | under 60 % of the rubric weight is assessable |
| Low confidence | 6 | 4 | 0 | conflicts or weak text quality |
| Prompt injection suspected | 4 | 1 | 0 | deliberate test CVs; flagged, not penalised |
| Language unsupported | 2 | 3 | 0 | non-English CVs go to a person |
| Below threshold / essentials weak (lower match) | 0 | 6 | 2 | evidence present but weak |
| Unreadable (processing error) | — | — | — | corrupt/encrypted files wait for HR, never lost (pilot: 6/100) |

Observations:

- *Review needed* is the largest band (95/135). Most *not suitable* CVs lack the essentials entirely,
  and absence is unknown rather than a fail. This is the intended conservative behaviour; it costs
  reviewer time, not candidates' chances. Clarification suggestions target exactly these gaps.
- No protected attribute appears in any band reason, score or explanation (protected leaks 0;
  counterfactual invariance 100 %).

## 6. Limitations and follow-ups

- Synthetic corpus only. Real-world calibration needs HR-labelled real applications under a pilot
  agreement (DPIA §6); until then bands remain routing hints.
- Host runs here had no OCR and (unless stated) no semantic model; the nightly `ai-benchmark` job
  covers both in the worker image.
- Fairness at scale (≥ 500 perturbations, proxy review) is P10-T04.
- D-008 is fixed and confirmed by the pilot rerun (`PILOT_BENCHMARK.md`, semantic on, no OCR on the
  host); no unsuitable or other-role CV was recommended.
